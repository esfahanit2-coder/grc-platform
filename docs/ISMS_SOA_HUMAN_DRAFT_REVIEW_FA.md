# ثبت بازبینی انسانی پیش‌نویس SoA — مرحله M1 از Issue #151

**مرز محصول:** این قابلیت **صرفاً درخواست نظر و ثبت بازخورد** درباره پیش‌نویس است. «بازبینی شد»، «نظر ثبت شد» یا «اصلاح خواسته شد» هیچ‌کدام به معنای تأیید SoA، امضای مسئول، انطباق ISO/IEC 27001، صدور گواهی یا کفایت شواهد نیستند. هیچ حالت `approved`، خروجی امضا یا انتشار در این مرحله وجود ندارد. `SoARegister.status` همیشه `draft` می‌ماند.

## داده و تاریخچه

مدل جدید `SoADraftReviewEvent` در برنامه `apps.reporting` برای هر پرونده و دور بازبینی دو رخداد حداکثری دارد:

۱. `requested`: درخواست نظر از بازبین مشخص و دارای مجوز در محدوده همان Tenant و واحد سازمانی؛ رخداد پاسخ نیست.

۲. یکی از `feedback_recorded` (صرفاً نظر متخصص، **نه تصویب**)، `changes_requested` (نیازمند اصلاح)، یا `superseded` (درخواست قبلی به‌دلیل تغییر داده منسوخ شده است). فقط یکی از این پاسخ‌ها برای هر دور ممکن است.

سوابق از طریق API قابل ویرایش یا حذف نیستند. ذخیره مجدد ردیف قبلی از طریق متد مدل و حذف مستقیم مدل نیز رد می‌شود. یک `AuditEvent` زنجیره‌دار موجود پروژه برای ارسال درخواست، ثبت پاسخ و منسوخ‌شدن دور ایجاد می‌شود. قابلیت‌های عمومی موتور `apps.workflows` در این مرحله برای `soa_register` **فعال نمی‌شوند**، زیرا Workflowهای قابل‌پیکربندی فعلی به‌تنهایی پیش‌شرط‌های حقوقی «Approved SoA» را اعمال نمی‌کنند. این یک دفتر بازخورد محدود است، نه موتور تصویب موازی؛ ادغام با موتور گردش کارِ مصوب در مرحله بعد انجام خواهد شد.

## API

- `GET /api/v1/soa/registers/{id}/review-requests/`: فهرست رخدادهای بازبینی در حوزه `report.view` و Tenant/واحد مجاز؛ شامل شناسه بازیگران، متن نظر، شماره دور، نوع رخداد و هشدار stale بودن نسخه؛ **بدون افشای Digest**.
- `POST /api/v1/soa/registers/{id}/review-requests/`: درخواست از بازبین مشخص `reviewer` به همراه `note` اختیاری. ایجادکننده باید مجوز `report.generate` در کل Tenant داشته باشد، بازبین باید عضو فعال باشد و مجوزهای واقعی `assessment.review` و `report.view` برای همان واحد داشته باشد. بازبین نمی‌تواند خودِ درخواست‌دهنده، سازنده اولیه پرونده یا آخرین ویرایشگر یکی از تصمیم‌های آن باشد.
- `POST /api/v1/soa/registers/{id}/review-requests/{event_id}/respond/`: صرفاً بازبین تعیین‌شده با همان دسترسی‌ها می‌تواند `kind=feedback_recorded` یا `kind=changes_requested` و `note` اجباری ارسال کند. هر نوع `approved` یا وضعیت دیگر رد می‌شود. پاسخ تکراری به یک دور باید رد شود.

## محیط فارسی کاربر

در `/soa/{id}` بخش «بازبینی انسانی پیش‌نویس» اضافه شده است که رخدادهای بازبینی را همراه با شماره دور، شرح نظر، وضعیت stale و امکان پاسخ فقط برای بازبین مجاز نمایش می‌دهد. برای درخواست نظر، فرم ابتدا بازبینان مجاز همان Tenant و واحد سازمانی را از مسیر زیر دریافت می‌کند:

`GET /api/v1/soa/registers/{id}/reviewers/`

این API فقط برای دارنده مجوز ایجاد پرونده (`report.generate` کل Tenant) قابل استفاده است و خروجی تنها شناسه و نام نمایشی حداکثر ۵۰۰ عضو دارای مجوز را نشان می‌دهد. وجود نام در فهرست باعث افزایش مجوز کاربر نمی‌شود؛ درخواست واقعی مجدداً در Backend بررسی می‌شود. اگر بازبین یا درخواست‌دهنده به فرم دسترسی نداشته باشد، پیام خطا دیده می‌شود. برای بازبین مجاز و فقط در صورت معتبر بودن Snapshot، دکمه «ثبت نظر بازبین» ظاهر می‌شود. هیچ گزینه «Approved»، امضا یا انتشار وجود ندارد.

این پنل فقط سوابق بازبینی را نمایش می‌دهد؛ ویرایش مستقیم رخداد یا برگشت پاسخ قابل انجام نیست. قابلیت جایگزینی نسخه جدید به درخواست بازبینی جدید نیاز دارد.

## جلوگیری از بازبینی نسخه قدیمی

برای هر درخواست یک Fingerprint محلی محاسبه می‌شود که شناسه Tenant/واحد، نسخه قفل‌شده و Checksum ثبت‌شده و بازحساب‌شده، تصمیم‌ها، توجیه‌ها، پیوندهای پیاده‌سازی و درمان ریسک و فهرست شواهد وابسته را دربر می‌گیرد. Fingerprint عمومی نیست و **امضای دیجیتال، اثبات اعتبار PDF یا هش رسمی ISO نیست**.

در هنگام پاسخ، محتوای فعلی دوباره محاسبه می‌شود. اگر تغییر کرده باشد، پاسخ با HTTP 409 رد می‌شود. درخواست‌دهنده می‌تواند دور تازه‌ای آغاز کند؛ دور قبلی با رخداد `superseded` بسته می‌شود و تاریخچه قبلی باقی می‌ماند. قفل تراکنشی روی SoARegister از دو پاسخ هم‌زمان و شروع دو دور یکسان جلوگیری می‌کند.

## محدودیت‌ها و مرحله بعد

- هیچ بررسی کفایت انسانی شواهد در سرور به صورت خودکار انجام نمی‌شود؛ بازبین تنها نظر انسانی ثبت می‌کند.
- دور پاسخ‌داده‌شده نه تأیید قانونی است و نه مجوز انتشار.
- Digest داخلی جایگزین مجوز استفاده از PDF و احراز حق نشر نیست.
- مجوزهای `assessment.review` و `report.view` فقط اجازه بازبینی پیش‌نویس می‌دهند؛ برای صدور رسمی نقش، مجوز و فرآیند مستقل با قفل نسخه نهایی و احراز حقوق منبع لازم است.
- مرحله M2 شامل طراحی رابطه امن با WorkflowInstance، تصویب مستقل دارای اختیار، Snapshot غیرقابل‌تغییر، ثبت امضا و حقوق استفاده از منبع فقط پس از مدارک واقعی و UAT است.

**معیار انتشار:** اجرای Migration بازگشت‌پذیر، آزمون واقعی دو Tenant، آزمون خودبازبینی، پاسخ شخص غیرمرتبط، فقدان حقوق، stale بودن پرونده، تاریخچه غیرقابل‌ویرایش، همه Checkهای Backend/Frontend/Security/Release Gate روی SHA دقیق، و بازآزمایی مستقل روی main.

Issueهای #143، #5، #68، #74 و #151 به‌دلیل عدم تحقق SoA نهایی و پذیرش عملیاتی باز می‌مانند.
