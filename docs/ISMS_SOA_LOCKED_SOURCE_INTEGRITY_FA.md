# کنترل یکپارچگی داخلی نسخه قفل‌شده Framework — Issue #149

این کنترل، مستقل از **اصالت منبع PDF، صحت مجوز استفاده از استاندارد، کفایت فهرست کنترل‌ها، صلاحیت بازبین یا امضای SoA** است. هدف صرفاً این است که پیش‌بررسی پیش‌نویس SoA به یک پرچم `is_locked=true` اعتماد نکند و Checksum محتوای خود پلتفرم را نیز کنترل کند.

## زیرساخت موجود که بازاستفاده می‌شود

`apps.frameworks.services.lock_framework_version()` هنگام قفل‌کردن نسخه، `calculate_version_checksum(version)` را روی ساختار داخلی و محتوای Requirements و ترجمه‌ها اجرا و SHA-256 را در `FrameworkVersion.checksum` ذخیره می‌کند. تابعی جدید برای هشِ رقیب یا منبع استاندارد ساخته نمی‌شود. هیچ محتوایی به مخزن عمومی از استانداردهای دارای حق نشر افزوده نمی‌شود.

## API و دامنه

`GET /api/v1/soa/registers/{id}/readiness/`

فقط کاربر مجاز برای همان Tenant و واحد سازمانی می‌تواند نتیجه را ببیند. در پاسخ موجود، بدون تغییر داده یا ساخت Migration، دو فیلد افزوده می‌شود:

- `locked_framework_content_integrity`:
  - `unlocked`: قفل نسخه فعال نیست.
  - `checksum_missing`: نسخه قفل شده اما Checksum موجود نیست. برخلاف تصور رایج این حالت **موفقیت** نیست.
  - `checksum_mismatch`: بازحساب Checksum با مقدار ثبت‌شده برابر نیست؛ نسخه باید کارشناسی بررسی شود.
  - `checksum_unverifiable`: در محاسبه متعارف به مشکل قابل کنترل برخورده‌ایم؛ وضعیت باید نامعتبر محسوب شود.
  - `internal_checksum_matches`: فقط **بایت‌های داده داخلی نسخه طبق الگوریتم canonical خود نرم‌افزار** با Hash ثبت‌شده هماهنگ‌اند. این نتیجه ادعای صحت محتوای ISO یا دارابودن حق استفاده نیست.
- `integrity_scope=internal_framework_requirement_content_only_not_pdf_or_licensing`: معنای دقیق محدوده بررسی.

سه نوع خطای نخست و خطای محاسبه‌ناپذیر در `register_findings` نیز به‌صورت قابل‌خواندن ماشین درج می‌شوند و در صفحه فارسی `/soa/{id}` نمایش داده می‌شوند؛ هیچ SHA، عنوان/بدنه Requirements یا محتوای PDF برای مصرف‌کننده API ارسال نمی‌شود.

## محدودیت‌های عمدی

- وضعیت `formal_attestation_allowed` همیشه `false` باقی می‌ماند.
- وضعیت `source_rights_review` همچنان `not_verified_by_this_endpoint` است.
- وضعیت `source_control_inventory_coverage` همچنان `not_verified` است.
- حتی با `internal_checksum_matches`، مرحله حقوق استفاده از استاندارد، احراز اصالت PDF خصوصی، محتوای کنترل‌ها، پیوندهای ریسک/شواهد و تایید مستقل انسانی **مسدود** باقی می‌ماند.
- این API Checksum را تعمیر نمی‌کند؛ بازقفل خودکار یا تغییر نسخه را انجام نمی‌دهد.

## آزمون‌ها و معیار پذیرش

۱. FrameworkVersion قفل‌شده ولی بدون Checksum باید هشدار `framework_content_checksum_missing` بدهد.

۲. قفل واقعی با `lock_framework_version` باید `internal_checksum_matches` بدهد ولی همچنان خروجی غیرقابل تأیید رسمی باقی بماند.

۳. تغییر آزمایشی Requirement پس از قفل با Update مستقیم باید `checksum_mismatch` ایجاد کند بدون افشای متن تغییرکرده.

۴. ازبین‌رفتن قفل پس از ساخت پرونده SoA باید `unlocked` و هشدار مربوط را ایجاد کند.

۵. تغییر داده ساختگی یک Tenant دیگر نباید در نتیجه این پرونده اثری بگذارد.

۶. آزمون‌های کامل Django/Frontend، امنیت، Release Gate، مرور شاخه و ادغام SHA-locked باید موفق باشند و بعد از ادغام نیز مستقل روی `main` اجرا شوند.

## ادامه پروژه

تأیید/امضای نسخه ثابت و نهایی SoA تنها بعد از تأمین مستندات مجوز، احراز قانونی اصالت منبع، انتخاب/استثنای کنترل‌های ضروری و کنترل‌های اضافی سازمان، بررسی شواهد و RTP، نقش امضاکننده مستقل و UAT مشتری امکان‌پذیر است. Issueهای #5، #68، #74 و #143 باز باقی می‌مانند.
